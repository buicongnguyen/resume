Q4-5: What exactly does zero-copy mean in your pipeline?

My answer

  1. DMA placed the data in host-memory buffers.
  2. The next software stage reused that data without an additional intermediate application-level copy.
  3. The GPU-transfer path is a separate part of the pipeline. Reusing the host buffer does not by itself mean that the digitizer writes directly into GPU memory.

Q4-6: How do you prevent a buffer from being reused while CUDA or the writer is still accessing it?

My answer

  1. C++ managed the buffer queues in my pipeline.
  2. The key rule is that a buffer can return to acquisition only after its last required consumer has finished using it.
  3. For asynchronous CUDA work, returning from the CPU function does not mean that the buffer is safe to reuse. If the GPU first copies input to separate device memory, the host buffer can be released after that copy completes, provided no other consumer needs it. If a kernel reads mapped host memory directly, I must wait until that kernel finishes reading it.
  4. The same applies to a writer that still references the buffer. Each stage needs a clear ownership transfer.

Study diagram — a proposed ownership rule, not a claim about the exact queue implementation. A consumer acknowledges its last access, not merely that its work was enqueued.

Study reference, not spoken: CUDA asynchronous execution and mapped host memory. A DMA buffer is not automatically eligible for CUDA mapping or asynchronous transfers; driver registration and supported memory properties must also be checked.

Q4-7: How would you implement a bounded producer–consumer queue?

My answer

  1. I would protect the queue state with a mutex and use condition variables for not-empty and not-full conditions.
  2. Each wait would use a predicate so spurious wakeups and shutdown are handled correctly.
  3. I would pass buffer handles rather than copy large payloads.
  4. Buffer recycling would wait for the final asynchronous consumer, and the design would include cancellation and error handling.
  5. I would test full and empty queues, blocked shutdown, multiple consumers, and delayed GPU or writer completion.

Q4-8: What if processing or SSD writing remains slower than acquisition?

My answer

  1. A queue can absorb a temporary stall, but it cannot solve a permanent throughput deficit.
  2. I would use bounded buffering and an explicit overload policy: reduce or pause acquisition if supported, or stop safely when the inspection requirement does not allow data loss.
  3. I would monitor queue depth and overflow status so the problem is visible before buffers are overwritten.
  4. Adding more buffers increases the time before overflow; it does not increase the downstream processing rate.

Q4-9: How would you prove that 50 kHz is sustainable without losing records?

My answer

  1. I would compare acquisition-event counts with completed records and check sequence continuity and overflow indicators.
  2. I would monitor the queue depth during a sustained run and confirm that processing and storage also finish at the required rate.
  3. The input bandwidth is acquisition rate times samples per record, channel count, and bytes per sample.
  4. I would include output formats and intermediate data in the bandwidth budget and compare against measured sustained transfer and SSD rates.

Q4-11: How does the FFT-based Hilbert method work?

My answer

  1. One common method constructs the analytic signal in the frequency domain.
  2. After the FFT of a real input, I retain DC (Direct Current, the zero-frequency bin), double the positive-frequency bins, and set the negative-frequency bins to zero. For an even-length input, I retain the Nyquist bin.
  3. The inverse complex transform gives the analytic signal. Its imaginary part is the Hilbert transform, and its magnitude gives the envelope.
  4. For a one-dimensional cuFFT forward/inverse pair of length N, I apply a total scale of 1/N, exactly once, because cuFFT does not normalize the transforms.

Implementation note, not spoken: this recipe needs a full complex spectrum for the inverse complex-to-complex transform. A real-to-complex forward FFT returns only the non-redundant half, so allocate and populate the full analytic spectrum before the inverse. Do not pass the doubled-positive, zero-negative analytic spectrum to a complex-to-real inverse: it is no longer Hermitian-symmetric. A separate method can compute only the real-valued Hilbert component using a suitably constructed Hermitian spectrum.

Study references, not spoken: analytic-signal construction and cuFFT transform types, Hermitian-input requirements, and normalization.

Q5-1: What was your scheduling task in TT-BUDA?

Q5-2: What is Ribbon2?

My answer — short version

  1. Ribbon2 is an existing balancing policy in TT-BUDA that I tested at Bos.
  2. Each operation can use a rectangular core grid. The policy tries different ribbon heights as starting points for choosing these grids.
  3. It compares candidate epoch configurations and adjusts the grids of slower operations to improve estimated utilization.
  4. My work was testing the existing policy and trying to improve scheduling and balancing.

Q5-3: Does ribbon simply mean an operation has a rectangular shape?

My answer

  1. The rectangle describes one operation's allocation of core rows and columns. It is not the shape of the input tensor.
  2. Ribbon height is a preferred number of core rows used when choosing operation configurations for an epoch.
  3. For example, with a ribbon height of two, three operations could use 2 by 3, 2 by 2, and 2 by 1 cores. They share the same height but use different numbers of columns.
  4. Those allocations could form a two-row strip if the placement and resource constraints allow it.
  5. The height is a starting preference, not a rule that every operation must keep the same height. The final configuration can differ as the policy optimizes the epoch.

Q5-4: How does Ribbon2 choose and improve an epoch configuration?

My answer

  1. It tries different ribbon heights for the current epoch.
  2. For each height, it selects legal operation configurations and uses the interactive placer to test core-grid fit.
  3. It estimates the candidate epoch's performance and identifies slower operations that limit the pipeline.
  4. It tries changing their grids, including assigning more cores, while checking whether the changes improve the candidate and still fit.
  5. It compares candidates, selects the higher-scoring configuration, and handles fork–join buffering. If buffering changes the graph or fit, it may need to evaluate the configuration again.

If they ask about the tradeoff

  1. Giving one operation more cores can make it faster, but leaves fewer cores for other operations in the epoch.
  2. If two configurations already meet the target cycle count, the selection logic can prefer fewer columns to save cores.
  3. The score is a performance estimate, not a measured utilization percentage. Prediction errors or local search limits can lead to a weaker choice, so I would compare estimates with measured execution.

Q5-5: Is Ribbon2 a topological-sort or ready-queue algorithm?

My answer

  1. Not exactly. A dependency-respecting scheduler determines which operation orders are legal.
  2. Ribbon2's candidate-building loop works through a supplied operation schedule and chooses configurations that can be placed in an epoch.
  3. Scheduling and balancing interact, but testing legal next-operation choices and choosing operation grids are different decisions.
  4. I would describe Ribbon2 mainly as an epoch-by-epoch balancing policy, rather than an exhaustive search of every legal operation order.

Q5-6: Does the 2 in Ribbon2 mean two rows or two dimensions?

My answer

  1. No. Ribbon2 can try different ribbon heights; it is not restricted to two rows.
  2. In the public code, the selectable policy is named Ribbon. There is a newer implementation in policy_ribbon2.cpp and a separate legacy implementation.
  3. I use Ribbon2 to identify the implementation I tested, not to describe a fixed grid shape.

Study references, not spoken: Ribbon2 candidate search, optimization, buffering, and limitations, grid-height preference and column selection, estimated epoch score, and Ribbon versus legacy policy dispatch.

Q5-7: What makes an operation ready, and does that mean it fits the current epoch?

My answer

  1. An operation is dependency-ready when its required producer operations have already been selected in the compiler's schedule. This is a compile-time decision, not a hardware-completion check.
  2. Being ready does not mean it fits. Its selected configuration still needs a valid grid placement and must satisfy per-core L1 and buffering constraints.
  3. If it cannot fit alongside the current operations, the compiler may try another candidate or configuration, or start a new epoch.
  4. If the configuration itself exceeds a core's L1 capacity, it needs a different supported configuration; an epoch break alone will not solve that.

Study diagram — compile-time scheduling and resource fit are separate checks.

Q5-8: How are scheduling, balancing, and placement different?

My answer

  1. Scheduling chooses a dependency-respecting operation order for the compiler.
  2. Balancing selects an operation configuration, including grid shape, blocking, and buffering, to balance performance and resource use.
  3. Placement assigns that configuration to actual core coordinates and epochs.
  4. These decisions interact: giving one operation more cores may improve its speed, but leave less space for other operations or change producer–consumer data movement.

Q5-9: What does reblocking mean on your slide?

My answer

  1. One operation can use a rectangular grid of k1 by k2 cores, with its tensor data distributed across those cores.
  2. If the consumer uses a different grid or block shape, the producer's tiles may need to be rearranged or redistributed. That is reblocking.
  3. Depending on the mapping, it can add buffering and data movement.
  4. My focus was checking producer–consumer layout compatibility when evaluating the schedule.

Q5-10: What determines epoch throughput and total model time?

My answer

  1. Operations pass data to their connected consumers, and their execution can overlap as a pipeline.
  2. In steady state, the slowest effective stage often limits throughput. I compare stages per model input, accounting for data movement rather than only math time.
  3. For epochs executed sequentially on one chip, I add their elapsed times and any transition or host overhead not already included.
  4. Estimating performance from the slowest operation in each epoch is useful for large batches, but it is not an exact single-input latency calculation. Pipeline fill, drain, and stalls also matter.

Q5-11: Why add buffering before an operation such as a + b = c?

My answer

  1. For a + b = c, the add operation needs the matching tiles from both inputs.
  2. If a arrives first, it waits in a buffer until the matching b arrives. They do not need to arrive at exactly the same time; the buffer holds data rather than adding a fixed delay.
  3. In a fork–join graph, if the earlier branch's buffer becomes full, it can block the shared producer and prevent the other branch from making progress. Extra buffering helps avoid that.
  4. TT-BUDA can increase input buffering in L1 (Level 1, the core's local memory). If necessary, it can insert buffering no-op operations or DRAM (Dynamic Random-Access Memory) queues.
  5. The buffer handles the difference in arrival time. It does not make the slower branch compute faster.

Study diagram — the join consumes matching input tiles; buffering permits different arrival times.

Study references, not spoken: interactive scheduler, balancer and operation-model definitions, TT-BUDA grid, reblocking, epoch-performance, and fork–join explanations, and Ribbon2 policy and fork–join buffering options.

Q5-12: Why can NoC congestion happen within a TT-BUDA epoch?

My answer

  1. The NoC (Network-on-Chip) carries data between cores and memory. Congestion happens when concurrent transfers compete for the same links or ports beyond their available bandwidth, so transfers have to wait.
  2. Within an epoch, several producer–consumer streams can share those routes. A placement can create a traffic hotspot even when other parts of the chip are lightly used.
  3. Different producer and consumer grid or block shapes may require gathering or redistributing tiles. This can add communication and put more pressure on shared routes.
  4. Sending separate copies of the same data to several consumers also adds traffic. Multicast can reduce those repeated transfers when applicable, and TT-BUDA already supports it.
  5. Having many operations in an epoch is not enough to prove congestion. What matters is where their data travels and how much traffic overlaps on shared resources.

If they ask: How would you distinguish NoC congestion from a compute bottleneck?

  1. I would separate compute time from time waiting for input, output, or synchronization.
  2. I would compare placements or transfer patterns while keeping the operation and numerical workload the same.
  3. I would inspect available traffic, stall, and timing information to see whether communication cost changes with the mapping.
  4. I would also check DRAM bandwidth, buffer availability, and synchronization. Low compute utilization alone does not prove NoC congestion.
  5. If compute utilization is low because data arrives late, optimizing only the math kernel is unlikely to solve the problem.

If they ask: How would you reduce the congestion?

  1. I would look for placements and compatible producer–consumer layouts that reduce unnecessary traffic on shared routes.
  2. I would reuse data locally and use multicast for shared data where the operation and compiler support it.
  3. I would compare alternative mappings or epoch configurations, checking measured end-to-end time as well as communication time. Reducing overlap can reduce contention, but can also reduce useful parallel work.

Study references, not spoken: Tenstorrent NoC estimator: contention between concurrent transfers, TT-BUDA multicast, TT-BUDA placement, reblocking, and performance analysis, and Metalium example: reduce redundant DRAM reads through data reuse and broadcast.

Matrix notation for this activation–weight example

  1. A (input activations) has M rows and K columns.
  2. B (weights, arranged for this multiplication) has K rows and N columns.
  3. C (the output matrix before bias or a nonlinear activation) has M rows and N columns: C = A × B.
  4. M is the number of input rows, such as samples, tokens, or output spatial positions in a convolution mapping. K is the input-feature reduction dimension; N is the output-feature dimension.

Layout notes for follow-up questions

  1. K means input features in a linear layer and input channels in a standard 1 by 1 convolution. For a standard dense convolution mapped to matrix multiplication, K includes input channels and kernel positions: K = input channels × kernel height × kernel width. N corresponds to output channels in this forward-convolution mapping.
  2. A and B are matrix labels, not universal abbreviations for activations and weights. Those are their roles in this example; other matrix multiplications can use different operands.
  3. The stored weight layout may differ. For example, PyTorch Linear stores weights W as N by K and computes with W transposed, so B = W transpose in our notation. Splitting B's output columns then corresponds to splitting W's output rows.

Q7-3: Explain why K-split (splitting input features) requires accumulation.

My answer

  1. For A (input activations) of size M by K and B (weights) of size K by N, K is the input-feature reduction dimension.
  2. I split A (activations) along its input-feature columns and the matching rows of B (weights).
  3. Each partition produces a partial result for the same output elements, so I add the partial results.
  4. That reduces the input data handled by a partition, but introduces partial-output storage, reduction traffic, and synchronization.
  5. Bias belongs after the sum, and a nonlinear activation generally cannot be applied independently to each partial result.

Q7-4: Why does N-split (splitting output features or channels) require concatenation instead?

My answer

  1. In this activation–weight example, N represents the output features or output channels. I split B (weights) by output-column ranges.
  2. Each partition produces different columns of C (the output), so I assemble those parts in column order rather than adding them.
  3. When the layout allows it, the partitions can write directly to separate output regions without an additional concatenation copy.
  4. The main cost to consider is distributing or rereading A (the shared input activations).

Study diagram — mathematical partitions of C = A × B. These may execute sequentially or in parallel; the equations do not prescribe one scheduling method.

Q7-5: How would you choose the split and validate it?

My answer

  1. I would start with the dimension causing the resource problem and calculate input, output, and temporary storage per core.
  2. Then I would compare the communication cost of K-split (input-feature splitting with accumulation) against N-split (output-feature splitting with shared input distribution).
  3. I would test uneven partitions and padding, compare numerical output with a reference, and check that every output range is written correctly.
  4. Finally, I would measure the complete operation and model. Fitting the operation and making it faster are separate results.

Q7-11: What is PCC, and why is passing a PCC test not enough?

  4. I would also check absolute and relative error, shapes, finite values, and sensitive output groups, then validate the model's task accuracy.
  5. I would choose thresholds from the operation, precision, and quality requirements. I would not copy one PCC threshold to every layer.

Q7-18: Can you explain that approach using deformable convolution as an example?

My answer

  1. A normal convolution samples a fixed spatial grid. Deformable convolution adds learned offsets to those sampling positions. Fractional positions require interpolation; the modulated version also multiplies each sampled value by a mask.
  2. I would first check whether an existing implementation supports my exact case. The reviewed TT-Metal UniAD example already has a TTNN decomposition, so I would evaluate that before building a new kernel.
  3. The decomposition is: calculate sampling coordinates, sample the input with bilinear interpolation, apply the modulation mask if present, then multiply by the convolution weights and accumulate across input channels and kernel positions. Bias is added once after the accumulation.
  4. In TTNN, the sampling stage can use a compatible grid_sample implementation, followed by multiply, reshape, matmul, and add operations. The UniAD example packs several sampling-coordinate sets together and splits large input-channel dimensions into chunks, then adds their partial outputs.
  5. I would check coordinate order, pixel-to-normalized coordinate conversion, align_corners, padding, convolution groups, and offset groups carefully. A correct shape alone does not guarantee that the samples come from the correct image positions.
  6. I would validate zero offsets with a unit mask against ordinary convolution, then test fractional offsets, image boundaries, non-unit masks, and real model inputs against the deformable-convolution reference. I would compare absolute and relative errors as well as the model's task accuracy.
  7. For performance, I would measure irregular memory reads, temporary sampled tensors, layout conversions, and the number of launches. If those dominate, I would consider a tiled custom implementation that combines sampling and masking and feeds the compute stage without materializing the entire expanded tensor.

If they ask: why not replace it with ordinary convolution?

  1. Learned offsets change where the operation samples the input, and a modulation mask changes the sampled values.
  2. Ordinary convolution removes those behaviors. It is equivalent only in the special case of zero offsets and a unit mask, with matching weights and convolution settings.
  3. Otherwise, that would be a model change, not just an implementation optimization, so it would require accuracy evaluation and potentially retraining.

If they ask: what limitations did you find in the public example?

  1. The reviewed UniAD helper asserts convolution groups equal to one and deformable groups equal to one. It also requires a square kernel and input channels that divide cleanly into its chosen chunks.
  2. It uses chunks of at most 256 input channels in that implementation. I would check those restrictions against the actual installed operator version instead of assuming that every deformable convolution is supported.
  3. Its base sampling grid can be reused for matching shapes, but the learned offsets and masks still need to be applied for each input. Caching the base grid is not caching the final input-dependent sampling locations.

JD 2 — Quantization, pruning, and compression

Common connection: model enablement or the matrix-multiplication discussion on slide 7.

QJD2-1: Is Tenstorrent BFP8 quantization? What does HiFi4 change?

My answer

  1. Yes. Converting higher-precision values to BFP8 (8-bit Block Floating Point) is numerical quantization: the values are rounded to the format's representable precision. It is not the same representation as affine INT8 quantization.
  2. In the documented BFP8_B format, groups of values share an exponent. This reduces storage, but values with very different magnitudes in the same group can lose precision.
  3. Math fidelity is separate from storage format. Modes such as HiFi4 (High-Fidelity Math Mode) control the matrix engine's computation phases.
  4. Higher fidelity cannot recover information already lost during input conversion, so I would validate the complete storage, multiplication, accumulation, and output path.

For the internal 19-bit operand registers and comparison with NVIDIA TF32, see QJD7-1.

QJD2-2: When would you use PTQ and when would you use QAT?

My answer

  1. I would usually try PTQ (Post-Training Quantization) first, starting from the trained model and evaluating lower-precision deployment.
  2. Static activation quantization uses representative calibration to choose ranges or parameters; weight-only and dynamic schemes may use a different process.
  3. If PTQ cannot meet the quality target, I would consider QAT (Quantization-Aware Training) or fine-tuning with simulated quantization effects.
  4. QAT costs more and still needs validation on the actual backend, because fake quantization does not reproduce every detail of the deployed arithmetic.

QJD2-3: How do pruning, sparsity, and compression improve performance?

My answer

  1. Structured pruning can remove channels, heads, or other regular dimensions, allowing smaller dense operations.
  2. Unstructured sparsity leaves an irregular zero pattern, so a suitable sparse execution path is needed to skip the work efficiently.
  3. Compression also includes lower precision, factorization, and storage encoding.
  4. I would distinguish checkpoint size, runtime memory, transferred bytes, and execution time. Improving one does not automatically improve the others.

QJD5-1: Is BFP8 the same as INT8 quantization?

My answer

  1. Both reduce numerical precision, but they represent numbers differently.
  2. BFP8 (8-bit Block Floating Point) shares an exponent across a group of values. Tenstorrent's BFP8_B format uses groups of 16 values.
  3. Affine INT8 (8-bit Integer) quantization instead uses a scale and zero point: round the value divided by the scale, add the zero point, and clamp it to the integer range.
  4. So I would not treat changing a tensor to BFP8_B as the same deployment path as an INT8 model with calibrated scales.
  5. I would check the consuming kernel's supported formats, its accumulation precision, and the final model quality.

Study references, not spoken: BFP8_B representation, shared-exponent calculation in blockfloat_common.cpp, and integer quantization implementation.

QJD5-2: How would you choose per-tensor or per-channel quantization in TT-NN?

My answer

  1. Per-tensor quantization uses one scale for the tensor. Per-channel quantization uses separate scales along a selected channel axis, which can help when channels have very different ranges.
  2. For convolution weights, I would normally evaluate separate scales per output channel, but I would first check the backend support.
  3. In the source version I reviewed, quantize supports INT32, INT8, and UINT8 output types, but explicitly rejects per-channel INT8 and UINT8 outputs. Its per-channel path supports INT32 output.
  4. That means I cannot assume a supported conversion function gives me a complete per-channel INT8 convolution pipeline.
  5. I would check the next operation's accepted types and scale handling, then measure any conversion cost. For a supported integer scheme, I would also test clipping, rounding, and zero-point behavior.

QJD5-3: How would you reduce a model to BFP8 without losing too much accuracy?

My answer

  1. I would first establish a correct higher-precision baseline and run representative inputs.
  2. I would lower precision one layer or tensor group at a time and compare intermediate outputs as well as the final task metric.
  3. For BFP8, I would examine outliers and values with different magnitudes sharing one exponent. Small values can lose precision even when the large values look accurate.
  4. I would keep sensitive layers or tensors in higher precision where the backend supports it, then measure whether the mixed-precision model still improves memory use and runtime.
  5. If further training is needed, I would use QAT (Quantization-Aware Training) or fine-tuning that reflects the target format. A generic INT8 fake-quantization setup does not automatically reproduce BFP behavior.
  6. I would validate the actual device conversion and compute path. Increasing math fidelity alone cannot restore information lost when storing the inputs.

QJD5-4: If I prune 80 percent of the weights, why might TT-Metal run at the same speed?

My answer

  1. Setting weights to zero does not necessarily change the tensor shape or the kernel's work.
  2. A dense kernel can still read the same tiles and execute the same matrix operations, including the zero values.
  3. For a speedup, I need either a smaller dense operation after structured pruning, or a sparse kernel that skips work at the granularity of my zero pattern.
  4. I would inspect the exported shapes and selected kernels, then measure transferred bytes and execution time. The percentage of zero weights alone is not a speedup measurement.
  5. For example, a pruning mask in PyTorch changes weight values, but does not by itself remove channels from the layer dimensions.

Study references, not spoken: PyTorch pruning masks and removal of reparameterization and TT-NN convolution execution paths. The performance conclusion follows from retaining the same dense shapes and execution path.

QJD5-5: How would you prune convolution channels safely and make the smaller model useful on an NPU?

My answer

  1. I would choose candidate channels using a quality-sensitive pruning method, then physically remove the selected output channels and their corresponding bias and normalization parameters.
  2. I also need to remove the matching input channels from downstream weights. For residual addition, both branches must keep compatible channel identities and order; concatenation requires updating the downstream channel mapping.
  3. I would check grouped or depthwise convolutions separately because pruning must preserve their grouping rules.
  4. After fine-tuning and checking model quality, I would regenerate the prepared weights and choose a new sharding and block configuration.
  5. I would compare the padded dimensions, not just the logical dimensions. A small channel reduction may leave the same number of hardware tiles, so it may save little compute.
  6. The useful result is a smaller, correct graph that runs faster on the target workload, rather than a high pruning percentage.

Study reference, not spoken: TT-NN convolution weight preparation, channel alignment, and parallel configuration. The graph-dependency checks are requirements of preserving the connected operations' shapes and channel semantics; they are a proposed pruning approach.

QJD5-6: Could low-rank compression be more useful than irregular sparsity?

My answer

  1. It can be, because it replaces one large dense multiplication with two smaller dense multiplications that may already have efficient kernels.
  2. For a weight matrix B of size K by N, I would approximate it as U of size K by r multiplied by V of size r by N.
  3. Instead of A multiplied by B, I compute A multiplied by U, then multiply that result by V. The parameter count changes from K times N to r times the sum of K and N.
  4. The rank r must be small enough to reduce work while preserving quality. I would also include the intermediate tensor, the second launch, tile padding, and any extra data movement.
  5. I would keep the original bias and nonlinear activation after the reconstructed linear operation. Adding a nonlinear activation between the two factors changes the function.

Memory aid, not spoken: parameter reduction requires r × (K + N) < K × N. This is low-rank approximation, not an exact replacement for an arbitrary matrix unless the chosen rank is sufficient. A is the input activation matrix; B is the original weight matrix; r is the chosen rank.

QJD5-7: Does Tenstorrent hardware compression mean sparse convolution is automatically faster?

  2. Tenstorrent's Wormhole hardware documentation describes a zero-run compressed format and unpacker decompression into compute registers.
  3. That can reduce L1 storage for suitable data, but the unpacker reconstructs values. It does not by itself prove that a convolution kernel skips zero multiplications.
  4. I would check whether the specific software path enables the format, and whether its metadata and processing overhead are worthwhile.
  5. I would then measure storage, data movement, and compute separately. I would verify the target architecture instead of assuming identical behavior across generations.

QJD5-8: What does sparse convolution mean, and how would you map it to Tenstorrent?

My answer

  1. I would first clarify the type of sparsity. Weight sparsity means many filter weights are zero. Spatial sparsity means only some input locations, such as occupied voxels, are active.
  2. For weight sparsity, I need a kernel that can skip the supported weight blocks or elements. Otherwise, structured channel pruning may be a simpler route to smaller dense convolutions.
  3. For spatial sparsity, I would build the input-output neighbor mapping, gather active features, perform grouped matrix work, and scatter or accumulate the results.
  4. I would measure the mapping, gathering, and scattering cost as well as the arithmetic. Irregular traffic and small matrix batches can remove the expected benefit.
  5. I would check whether TT-NN has a supported operation matching those semantics. A function named sparse_matmul is not automatically a replacement for an arbitrary sparse convolution.

Study references, not spoken: spatial and submanifold sparse-convolution semantics and TT-NN sparse-matmul validation and supported modes. The gather–compute–scatter mapping is a proposed implementation strategy, not a claimed TT-NN sparse-convolution implementation.

QJD5-9: What kind of sparsity does the TT-NN sparse_matmul implementation actually support?

My answer

  1. In the implementation I reviewed, sparsity selects which batch or group matrix multiplications run. It is not a mask for every individual weight inside a matrix.
  2. For example, B can contain E expert weight matrices. A mask selects which activation–expert pairs to compute, which is useful for MoE (Mixture of Experts) workloads.
  3. The current interface also has an indexed mode that directly lists active group IDs and returns a compact group dimension. The selected matrix multiplications still use tiled operands.
  4. So I would first check whether my workload's sparsity matches that group-level selection. Arbitrary zero weights or spatial convolution coordinates need a different mapping.
  5. I would compare the selection overhead, selected matrix sizes, data movement, and load balance against a dense baseline.

Study references, not spoken: sparse_matmul API and modes, device-operation validation, including indexed mode, and expert-mask test examples. E means the number of expert or sparse-group matrices, not an individual-element sparsity dimension.

QJD5-10: Why could incorrect sparsity metadata cause a hang rather than only a wrong result?

My answer

  1. In the mask-based sparse_matmul path, nnz means the number of nonzero mask entries, not the number of nonzero weights.
  2. If supplied, it must match the mask exactly. The sender and the receiver/compute kernels otherwise disagree about how many transfers and computation steps should happen.
  3. That can leave a kernel waiting for data or synchronization that never arrives. The code documents this risk and provides an on-device check under Watcher.
  4. I would generate the mask and count consistently, or omit nnz and use the supported runtime-inferred path. I would test edge cases and enable Watcher during validation.
  5. This is why I treat sparse metadata as part of execution correctness, not just a hint for performance.

Study references, not spoken: nnz consistency checks and sender/receiver loop explanation and API warning. Watcher is TT-Metal's device-side checking/debugging facility. Indexed mode has different metadata rules; the supplied-nnz discussion here is specifically about the mask-based path.

QJD5-11: What is im2col, and how does it connect convolution to the K-split and N-split example?

My answer

  1. Im2col means image-to-column. It rearranges convolution windows into matrix data. Using the orientation in my slide, each flattened window is one row of A, the activation matrix.
  2. For a standard dense convolution, M is batch size times output height times output width. K is input channels times kernel height times kernel width, and N is output channels.
  3. B contains the flattened filters, so the convolution becomes C equals A multiplied by B, followed by bias or activation if required.
  4. K-split divides each window and the matching filter entries, then sums partial outputs. N-split divides the output filters and assembles separate output channels.
  5. A fully materialized im2col matrix duplicates overlapping input values. For a stride-one 3 by 3 convolution with unchanged spatial dimensions, its logical activation volume is about nine times the input volume.
  6. That is why I would prefer gathering windows in blocks when possible, instead of writing the entire expanded matrix to device memory.

Memory aid, not spoken: A: M × K; B: K × N; C: M × N. These dimensions describe a standard dense forward convolution. Grouped convolution uses a separate input-channel subset per group.

Study reference, not spoken: Tenstorrent's convolution-to-matrix mapping. “Image-to-column” is the conventional name; the row-oriented formulation above is its transposed layout, chosen to match slide 7.

QJD5-12: Does TT-Metal always create a complete im2col matrix in DRAM?

My answer

  1. No. The matrix formulation does not require the whole expanded matrix to be stored in DRAM (Dynamic Random-Access Memory).
  2. In the sharded convolution path I reviewed, the code sets up sliding-window information and conditionally prepares halo data.
  3. An activation reader uses prepared indices and window offsets to gather input data into local buffers in blocks. The compute kernel consumes those blocks for matrix multiplication.
  4. The reader code includes dilation-aware reads and coalesces adjacent data where the configuration allows it. That is more specific than saying convolution is just a reshape.
  5. There is also a separate matrix-multiplication path for eligible 1 by 1 convolutions. The selected path depends on the convolution parameters and configuration.

Study references, not spoken: conv2d path selection and conditional halo call, activation-window reader and reader-index buffers, and reader/compute pipeline explanation. This describes the reviewed paths, not a universal implementation for every convolution variant.

QJD5-13: What is halo exchange, and why can it become a convolution bottleneck?

My answer

  1. A shard can need input values owned by a neighboring shard to compute output windows near its boundary. Halo preparation makes those required values available locally.
  2. Halo data is real neighboring input. Padding is different: it supplies values such as zeros outside the image boundary.
  3. Preparing halos can reduce remote activation reads during window processing, but it adds data transfer, duplicated storage, and preparation time.
  4. I would compare sharding choices and measure halo time together with convolution time. More cores can reduce work per core but increase boundary overhead.
  5. I would also tune activation blocks and buffering within L1 capacity. Double buffering may overlap stages, but its extra storage can make an otherwise useful configuration fail to fit.

Study references, not spoken: halo and sharding explanation, conditional halo setup, and convolution configuration tradeoffs.

QJD5-14: Given a slow YOLOv8 convolution, how would you decide between quantization, pruning, sparsity, and kernel tuning?

My answer

  1. I would first measure the actual operator path: input preparation, halo, layout conversion, matrix computation, output handling, and dispatch.
  2. If data movement dominates, I would consider better sharding and reuse, fewer layout conversions, and supported lower-precision storage. I would include any conversion overhead.
  3. If dense computation dominates, I would tune the matrix blocks and compute configuration, then evaluate structured pruning or lower precision against the quality target.
  4. I would try sparse execution only when the zero pattern matches a supported kernel and enough work is skipped to pay for metadata and irregular access.
  5. After a shape or precision change, I would retune the configuration and prepared weights rather than reuse an unsuitable setup.
  6. I would compare warm end-to-end latency, throughput, memory use, and detection quality on representative inputs. The decision comes from the measured model result, not just fewer parameters or operations.

JD 6 — TT-Metal follow-ups — sharding and DRAM interleaving

Use these for data-movement questions during slides 5–7. Start with QJD6-1–QJD6-3 for the concepts, QJD6-4 for configuration, and QJD6-6–QJD6-10 for performance and debugging.

Study note, not spoken: checked against the same TT-Metal revision as the preceding section. Examples describe a proposed setup, not a configuration claimed for the Bos project. The code example assumes an initialized device with the selected logical cores available; it has not been executed on an NPU in this review.

QJD6-1: How are tiled layout, interleaving, sharding, L1, and DRAM different?

My answer

  1. They describe different choices. Tiled or row-major layout describes how tensor elements are arranged inside memory pages.
  2. Interleaving or sharding describes how those pages or tensor regions are distributed across memory banks.
  3. L1 or DRAM (Dynamic Random-Access Memory) describes where the data is stored. L1 is on-chip SRAM (Static Random-Access Memory); in this programming model, it is explicitly managed storage rather than a transparent data cache.
  4. So a tiled tensor can be DRAM-interleaved or L1-sharded. L1-interleaved and supported DRAM-sharded configurations also exist.
  5. My choice needs to match both the operation's supported layouts and where its cores will read the data.

Study references, not spoken: tensor and memory layouts and explicit SRAM management in Metalium. This section discusses distribution within one device. Splitting a tensor across multiple devices is a separate level of sharding.

QJD6-2: What exactly happens when a tensor is interleaved across DRAM banks?

My answer

  1. In the usual interleaved layout, consecutive pages are distributed across banks in round-robin order.
  2. For a simple four-bank example, pages zero, one, two, and three go to banks zero through three. Pages four through seven repeat that bank order at the next page position.
  3. That distributes storage and gives readers access to multiple banks, but it does not guarantee balanced traffic. The actual access pattern may repeatedly select only some pages or overload shared NoC (Network-on-Chip) routes.
  4. In a tiled tensor, the page is commonly a tile. A page is not a host operating-system page or hugepage.
  5. In a kernel, I would use the supported tensor address accessor to translate a logical page index. I would not treat all pages as one physically contiguous DRAM region.

Memory aid, not spoken: in the simplified round-robin example, bank = page index modulo bank count, and page position within that bank = integer division of page index by bank count. Physical bank coordinates, aligned page stride, and base addresses still come from the device mapping.

Study references, not spoken: interleaved page distribution and TensorAccessor in a working reader example.

QJD6-3: How would you explain height, width, and block sharding with a simple example?

My answer

  1. For the conventional two-dimensional sharding scheme, I flatten all dimensions except the last into height. The final dimension becomes width.
  2. Take a 256 by 256 tensor and four cores. Height sharding gives each core 64 complete rows, so each shard is 64 by 256.
  3. Width sharding gives each core 64 complete columns, so each shard is 256 by 64.
  4. Block sharding over a two-by-two grid gives each core a 128 by 128 block.
  5. I choose the split according to what the operation consumes. The shard orientation also matters because it determines the order in which logical shards map onto the selected cores.

Study reference, not spoken: height, width, and block sharding. Height and width here refer to the tensor's two-dimensional representation, not necessarily the original image height and width.

QJD6-4: How would you configure a DRAM-interleaved tensor and then shard it into L1?

My answer

  1. I would first create the tensor with the required data type and tensor layout in DRAM-interleaved memory.
  2. Then I would define the logical core set, sharding strategy, per-core shard shape, and shard orientation.
  3. For the four-core height-sharded example, I would specify L1 storage and a 64 by 256 shard on each core.
  4. I would use the supported memory-conversion operation to move the tensor into that configuration, then verify the values after a round trip.
  5. Before using the tensor in a real operation, I would check that its program configuration accepts this core set and shard shape. A valid allocation is not enough to guarantee a compatible kernel.

Small configuration example, not spoken:

# Assumes torch and ttnn are imported and device is already open.
host = torch.randn((256, 256), dtype=torch.bfloat16)
x_dram = ttnn.from_torch(
    host, device=device, dtype=ttnn.bfloat16,
    layout=ttnn.TILE_LAYOUT,
    memory_config=ttnn.DRAM_MEMORY_CONFIG,
)

cores = ttnn.CoreRangeSet({
    ttnn.CoreRange(ttnn.CoreCoord(0, 0), ttnn.CoreCoord(1, 1))
})
shard_spec = ttnn.ShardSpec(
    cores, [64, 256], ttnn.ShardOrientation.ROW_MAJOR
)
height_l1 = ttnn.MemoryConfig(
    ttnn.TensorMemoryLayout.HEIGHT_SHARDED,
    ttnn.BufferType.L1, shard_spec,
)

x_sharded = ttnn.to_memory_config(x_dram, height_l1)
x_back = ttnn.to_memory_config(x_sharded, ttnn.DRAM_MEMORY_CONFIG)
torch.testing.assert_close(ttnn.to_torch(x_back), host, rtol=0, atol=0)

Study references, not spoken: explicit MemoryConfig and ShardSpec examples and to_memory_config API. ShardOrientation.ROW_MAJOR controls shard-to-core ordering; it does not change the tensor's TILE_LAYOUT.

QJD6-5: How do you know whether an L1-sharded configuration will fit?

My answer

  1. I would calculate the peak live memory on each participating core rather than rely on the total L1 capacity across the chip.
  2. A 64 by 256 shard in BF16 (Brain Floating Point, 16-bit) contains 32 KiB of values. Input, output, and temporary buffers can coexist, so one shard's size is only the starting point.
  3. I would add padded storage, separate circular buffers, double buffers, halo data, runtime-reserved memory, and other live tensors.
  4. If a circular buffer aliases an existing shard allocation, I would count the shared storage once. Separate allocations must be counted separately.
  5. If it does not fit, I would consider smaller working blocks, shorter tensor lifetimes, another supported core partition, or streaming from DRAM. I would verify the actual allocation report and alignment constraints.

Study references, not spoken: allocator, reserved regions, alignment, and circular buffers and convolution buffering tradeoffs. KiB means kibibyte: 1,024 bytes. A capacity check uses padded allocation sizes and the target device's available memory.

QJD6-6: When would you use DRAM-sharded weights instead of DRAM interleaving?

My answer

  1. I would consider it when weight reads are the bottleneck, for example a small-M matrix multiplication with few activation rows and large weights.
  2. DRAM sharding assigns tensor partitions to banks. A suitable kernel organizes its readers around those partitions, reducing scattered bank access and unfavorable NoC routes.
  3. Tenstorrent's bandwidth report demonstrates bank-local readers and overlapped transfers. Its matmul example combines DRAM-sharded weights with L1-sharded activations.
  4. I would use a matching DRAM-sharded matmul program configuration, checking shard padding, reader placement, and the actual available bank count.
  5. I would not assume one reader per bank is always required. The newer test code includes configurations with multiple workers per bank.
  6. I would compare the full operation, including activation distribution and output movement. Interleaved DRAM remains a useful baseline, and sharding is not automatically faster for every shape.

Study references, not spoken: DRAM-bandwidth technical report and current DRAM-sharded matmul tests and worker counts. The test uses MatmulMultiCoreReuseMultiCastDRAMShardedProgramConfig. Its DRAM shard grid describes banks; an L1 shard grid describes worker cores. Do not substitute one coordinate set for the other or hard-code one architecture's bank count.

QJD6-7: At the low level, how does a reader safely bring interleaved data into a core?

My answer

  1. I would pass the tensor's layout information and base address, plus the logical page range assigned to that reader.
  2. The TensorAccessor maps each logical page to the correct device address. The reader first reserves free space in its CB (Circular Buffer).
  3. It issues asynchronous NoC reads into that space and waits for the required transfer completion before publishing those pages to the compute kernel.
  4. The compute side waits for available input and releases consumed pages. That prevents the producer from reusing storage while the consumer still needs it.
  5. After establishing correctness, I would pipeline reads with computation using separate buffers and the appropriate completion mechanism. Waiting after every tiny request can leave DRAM idle, but removing waits without preserving buffer ownership is unsafe.

Study references, not spoken: reserve, read, barrier, and publish sequence and overlapping tagged DRAM transfers. The report's transaction-tag technique is one implementation example; the required synchronization depends on the selected API and architecture.

QJD6-8: How does the sharding choice connect to M-split, K-split, and N-split in matrix multiplication?

My answer

  1. For C equals A multiplied by B, A is M by K, B is K by N, and C is M by N. In this example, A contains activations and B contains weights.
  2. Splitting M assigns different activation rows and output rows to different workers. They still need the corresponding weights.
  3. Splitting N assigns different weight columns and output channels to different workers. Those workers need the shared activation data.
  4. Splitting K divides the reduction: matching parts of A and B produce partial values for the same outputs, which must be accumulated.
  5. Width-sharding A therefore splits K, while width-sharding B splits N. The same word “width” has a different computational meaning for each operand.
  6. I would choose a supported program that supplies the missing operand data through reuse, multicast, or another transfer scheme. A memory shard specification alone does not define the complete computation schedule.

Study references, not spoken: matmul configuration and operand distribution and logical A/B tile indices in the reader. This is a mathematical partitioning explanation, not a promise that every operand layout combination is accepted by every matmul kernel.

QJD6-9: Is changing the memory configuration just metadata, and does L1 sharding eliminate NoC traffic?

My answer

  1. A change in physical placement generally needs data movement, allocation, and synchronization. It is not just changing a label.
  2. L1 sharding helps when the consuming core already owns the data it needs. Remote shards, shared weights, reductions, and convolution halos can still require NoC traffic.
  3. I would try to make one operation's output layout suitable for the next operation, so the pipeline avoids repeated resharding or trips through DRAM.
  4. I would distinguish memory conversion from tilization. Changing DRAM/L1 placement or shard distribution is different from rearranging row-major elements into tiles.
  5. I would measure the producer, conversion, and consumer together. A faster consumer can still make the pipeline slower if its required conversion is expensive.

Study references, not spoken: to_memory_config, memory conversion versus retiling in the TT-NN optimizer, and producer/consumer memory configurations.

QJD6-10: A sharded kernel is slower or gives wrong results. What would you check first?

My answer

  1. For correctness, I would check logical and padded shapes, shard shape, core order, and the kernel's input/output requirements.
  2. I would use a small tensor with an identifiable pattern, verify each shard and the reconstructed result, and check boundary tiles and uneven partitions.
  3. For a hang, I would also check buffer ownership, transfer completion, and agreement between the number of produced and consumed pages.
  4. For performance, I would separate conversion time, bank reads, NoC transfers, compute, and waits. I would look for uneven work or one slow core delaying completion.
  5. I would vary the grid, block size, and buffering one at a time while keeping the workload and accuracy requirement fixed. More cores are useful only when their added parallelism outweighs communication and coordination costs.

Study references, not spoken: shard specifications, DRAM reader-placement and congestion examples, and matmul validation tests. These are proposed diagnostic steps, not an additional incident claimed from Bos.

QJD7-1: I have heard that Tenstorrent calculates with 19 bits. Is that similar to NVIDIA TF32?

My answer

  1. Yes, the comparison is useful for a specific part of the matrix path. Tenstorrent documents SrcA and SrcB as matrix-input registers holding values up to 19 bits wide.
  2. One supported representation is explicitly called TF32 (TensorFloat-32): one sign bit, eight exponent bits, and ten stored fraction bits.
  3. NVIDIA TF32 also uses that exponent and fraction width for matrix multiplication, with FP32 (32-bit Floating Point) accumulation in the documented Tensor Core path.
  4. But the source-register width is not the precision of every operation. Tenstorrent's input storage format, math fidelity, destination accumulation, and packed output format are separate choices.
  5. For example, unpacking BFP8 into a wider internal representation does not recover precision already lost in BFP8 storage. I would validate the complete numerical path rather than judge accuracy from “19-bit” alone.

Study references, not spoken: Tenstorrent SrcA/SrcB types and fidelity phases, NVIDIA TF32 multiplication with FP32 accumulation, and Tenstorrent matrix-engine accumulation controls.

Deeper accuracy note, not spoken unless asked: the cited Tenstorrent register documentation says the least-significant TF32/FP16 fraction bit in SrcA is not used by the multiplication instructions it describes. It also documents format-specific behavior that is not fully IEEE 754-compliant. Matching the nominal TF32 bit fields therefore does not establish bit-identical NVIDIA and Tenstorrent arithmetic. Keep this scoped to the documented architecture and instruction path. TF32 also does not mean ordinary NVIDIA tensors occupy packed 19-bit elements in memory.

QJD8-1: What techniques make TT-Metal execution fast?

My answer

  1. I separate these techniques by the cost they reduce: building the program, submitting work, transferring data, and executing the kernel.
  2. Fast Dispatch and prefetching — between the host and device workers: the host queues work, while device-side prefetch and dispatch stages deliver commands and payloads to worker cores. This supports overlap between command delivery and execution; it does not make the math instructions themselves faster.
  3. Program cache — in the host-side TTNN/Metalium runtime: for a compatible operation, the runtime reuses its prepared program and updates supported runtime arguments, such as buffer addresses. This is useful for repeated matmul or convolution calls with compatible configurations; the operation still computes a new result from the current input.
  4. Kernel-build cache — in the host build system and its disk cache: compatible compiled binaries can be reused instead of compiled again. This mainly helps startup or first-use preparation, rather than the execution time of an already-running kernel.
  5. Metal Trace — around a repeated operation sequence: the host controls capture and replay, and the captured command buffer is stored in device DRAM. For example, I would evaluate it for a fixed-shape vision-model forward pass. It reduces repeated host submission work but requires compatible shapes and the captured buffer addresses.
  6. Multiple command queues — in the host-to-device inference pipeline: with explicit events and safe buffer reuse, I can overlap transfers for another request with computation. This can improve a stream of image requests, but it does not guarantee lower latency for a single request.
  7. Kernel data flow — inside operations on the worker cores: tensor placement in DRAM and L1, operand reuse, NoC multicast, and double buffering can reduce repeated transfers or overlap them with computation. Their value depends on the operation's layout, memory capacity, and actual bottleneck.
  8. I would measure the bottleneck first. A compile cache helps repeated builds, Trace helps host-bound execution, and data-flow changes help a kernel that is waiting for data.

Memory aid: build less → prepare less → submit less → overlap transfers → move less data. Fast Dispatch supplies the queued execution path; program caching and Trace reduce different work above that path.

Study diagram — these mechanisms reuse different objects; none caches the numerical answer for a new input.

QJD8-2: How do Fast Dispatch and prefetching work together?

My answer

  1. This is used in the runtime's command-delivery path, below the model's TTNN calls. The host prepares queued commands, and device-side service kernels deliver the work to the worker cores that execute the operation kernels.
  2. The prefetch stage fetches commands and required payloads from host memory or device DRAM, depending on the path, and feeds the downstream dispatcher.
  3. The prefetch code uses staging buffers and a readiness/completion protocol with the dispatcher. That allows fetching and downstream processing to overlap without overwriting unread data.
  4. This reduces launch and delivery overhead, but it does not make the matrix engine's individual instructions faster or remove operation dependencies.
  5. Dispatch prefetching is also different from a compute operation prefetching its next activation or weight block. Both can overlap work, but they operate at different levels.

Study references, not spoken: prefetch kernel, queues, and dispatcher synchronization and official dispatch-pipeline description. The conceptual path is host → prefetch → dispatch → workers; the physical placement and number of service cores depend on the configuration and architecture.

QJD8-3: What does the program cache save, and what must still change on a cache hit?

My answer

  1. This cache lives in the host-side runtime and is associated with the device handle. It saves a prepared program or workload and the associated setup state for a compatible operation configuration, not the operation's numerical output.
  2. For example, repeated TTNN matmul calls with a compatible configuration can reuse the prepared program. A cache hit avoids rebuilding it, but the operation still executes on the current inputs.
  3. The runtime must refresh supported dynamic information, such as input and output buffer addresses, through the program's argument-update path.
  4. The cache key must distinguish the properties that change the generated program, such as relevant shapes, layouts, data types, and operation settings. The exact key is operation-specific.
  5. For a custom operation, I would test repeated calls with different values and newly allocated buffers. I would also test changes in shapes or configurations to catch incorrect reuse or stale arguments.

Study references, not spoken: cached programs, shared variables, and cache-key structure, operation hashing and runtime-argument overrides, and first-run versus cached-run example. A program-cache hit is not a guarantee that every host-side cost disappears; that is why trace replay can provide an additional benefit.

QJD8-4: How do program caching, persistent kernel caching, and ccache (compiler cache) differ?

My answer

  1. The program cache keeps reusable program objects in the host process, associated with the device handle. It helps repeated compatible operation calls in that runtime session.
  2. A persistent kernel-build cache keeps compiled artifacts on the host's disk so a later run can reuse compatible binaries instead of compiling them again. It is used during kernel preparation, before the binary is loaded and executed on the device.
  3. The reviewed JIT (Just-In-Time) build code checks for a reusable ELF (Executable and Linkable Format) binary, matching build state, and up-to-date dependencies.
  4. Source, compiler, build flags, or link inputs can invalidate reuse. For a linker-related debug change, I would verify that the rebuilt ELF is actually the one being loaded.
  5. ccache (compiler cache) is a tool used around compiler invocations on the host to reuse compatible compilation results. It speeds up rebuilding code, not the computation inside an already-built kernel. TT-Metal's build code has an optional ccache path, separate from the runtime program cache.
  6. These caches mainly reduce preparation and compilation costs. They do not replace the computation or automatically reduce steady-state memory traffic.

Study references, not spoken: JIT build reuse, compiler identity, link dependencies, and optional ccache and in-process build-once coordination. The latter avoids duplicate builds of the same key within a process; it should not be confused with disk persistence. Recheck the installed release before using a remembered enable-cache API name.

QJD8-5: If the program cache is already warm, why can Metal Trace still improve performance?

My answer

  1. A warm program cache avoids rebuilding programs, but the host still calls operations and prepares their normal dispatch submissions.
  2. Metal Trace records an operation sequence's dispatch commands in a device DRAM buffer, then replays that sequence with much less repeated host work.
  3. I would use this at the model-runner level, around a repeated forward pass or stable subgraph. I would warm up the required operations, allocate sufficient trace memory, capture the sequence, and replay it for compatible requests.
  4. In the documented capture path, shapes and buffer addresses are recorded. I would update data in the expected buffers and keep their addresses and lifetimes valid.
  5. Input copies and output readback need their own ordering around replay. If the sequence or captured configuration changes, I would use an appropriate separate capture rather than assume the old trace adapts automatically.
  6. I would expect the biggest benefit when host overhead leaves gaps between short operations. A long compute-bound kernel may gain much less.

Study reference, not spoken: Metal Trace capture, persistent buffers, and replay requirements.

API memory aid, not spoken: allocate the device's trace region; warm up; use begin_trace_capture → operation sequence → end_trace_capture; then execute_trace for later runs. Synchronize completion before consuming results. This describes the documented capture workflow, not every possible future dynamic-trace interface.

QJD8-6: How would you overlap transfers and computation with multiple command queues safely?

My answer

  1. I would configure this in the host-side inference loop when opening the device: two supported command queues, one for transfers and one for operation execution. For a stream of images, I would use separate buffer slots where work overlaps.
  2. The execution queue must wait for the input-ready event before consuming a slot written by the transfer queue.
  3. The transfer queue must also wait until that slot is no longer being read before overwriting it with another request. Output storage needs the same lifetime discipline.
  4. With that ordering, I can transfer the next request into a free slot while computing the current request from another slot.
  5. If I combine this with trace replay, the selected slot must match the trace's captured buffer addresses.
  6. I would measure actual overlap and end-to-end throughput. Adding queues cannot remove a shared bandwidth bottleneck and may not reduce one request's latency.

Study references, not spoken: multiple command queues, events, and trace integration and event recording and waiting examples. CQ means Command Queue. The buffer-slot explanation is a proposed pipeline design; the required reuse event depends on when the last reader finishes.

QJD8-7: How would you prove which of these optimizations actually helps?

My answer

  1. I would report initialization and first-use compilation separately from warm steady-state execution.
  2. I would compare a warmed Fast Dispatch baseline, trace replay, and any multi-queue pipeline while keeping the workload, numerical settings, and correctness checks fixed.
  3. I would measure both host elapsed time through completion and device execution time. Timing only an asynchronous enqueue call would not measure completed inference.
  4. I would inspect gaps between operations, transfer overlap, cache misses, and device compute or memory stalls to explain the result.
  5. If warm execution is already compute-bound, I would focus on kernel blocks, precision, or data reuse rather than expect compilation caching to make the computation faster.
  6. I would also test repeated runs with changing input data to ensure that caching and replay reuse the execution setup, not stale data.

QJD8-8: How do sharding, operand reuse, multicast, and double buffering speed up a kernel?

My answer

  1. Sharding is selected through tensor memory configuration and supported operation configuration. It places tensor partitions in worker-core L1 memory or DRAM banks. I would match that partition to each worker's input needs; a poor layout can add redistribution or leave some cores with more work than others.
  2. Operand reuse is implemented in the operation's blocked data-movement and compute loops. In matrix multiplication, an activation or weight block can contribute to several output tiles. Keeping it in L1 or registers for those calculations reduces repeated reads, within the available capacity.
  3. Multicast is used by data-movement kernels over the NoC (Network-on-Chip). When multiple cores need the same activation block, a supported multicast can avoid separate source sends to every core. It is useful for shared operands, not for unrelated data, and still uses bandwidth and needs receiver synchronization.
  4. Double buffering is used between the reader and compute stages, commonly through L1 circular-buffer capacity for successive blocks. While compute consumes block zero, the reader can load block one into free space. Compute waits until its input is ready, and the producer cannot overwrite a slot until its consumer has finished.
  5. The tradeoff is memory and synchronization. Larger blocks or more buffering may improve reuse and overlap, but they consume L1 capacity. I would check that the chosen blocks, circular buffers, and other program allocations fit together.
  6. I would validate the numerical output, then measure DRAM traffic, NoC pressure, and compute stalls. More cores or larger buffers are not automatically faster if they increase traffic or imbalance.

If they ask for a concrete example

  1. In Tenstorrent's documented DRAM-bound matrix multiplication example, each reader fetches its weight partition from an assigned DRAM bank, while shared activation shards are multicast to the compute cores.
  2. The input blocks are double buffered so movement can overlap computation. Reader placement also matters because overlapping NoC routes can limit bandwidth.
  3. I would treat this as a design to evaluate for a similar workload, not as a rule that every tensor should use the same sharding or multicast pattern.

Study reference, not spoken: official DRAM-bandwidth report — sharded matmul, reader placement, multicast, and double buffering. This example is architecture- and workload-specific. QJD8-9: For repeated fixed-shape inference, how would you combine these techniques step by step?

My answer

  1. Establish a correct baseline in the model runner. For example, with a repeated fixed-resolution vision-model input, I would run the model with Fast Dispatch and compare its outputs with the reference. I would measure the first run separately from warmed execution.
  2. Warm the program and kernel caches. The first use prepares the required operation programs and compiles any missing kernels. Later compatible calls reuse that work, while still processing new input values.
  3. Check where time is lost. If there are large host-side gaps between short operations, I would evaluate Metal Trace. If the device spends most of its time inside a memory-bound kernel, I would first investigate its layout and data reuse.
  4. Capture the stable operation sequence. For Trace, I would allocate enough trace memory, retain valid buffers at the captured addresses, and capture the warmed operations. For each new request, I would copy new data into the expected input buffer, replay, and wait for completion before using the result.
  5. Overlap requests only after that works. I would use supported command queues and events so input transfer can overlap another request's computation. A shared input slot becomes reusable only after its last reader finishes; using another slot also requires a trace compatible with that slot's addresses.
  6. Compare completed work. I would compare warm inference latency and sustained throughput with the same shapes, precision, and correctness criteria. Timing an asynchronous submission alone would hide work still running on the device.
  7. Keep only useful changes. Trace does not remove the kernel's computation, and extra queues do not increase physical DRAM or PCIe bandwidth. I would keep a technique when the measured gain justifies its memory and synchronization cost.

If they ask: why use Trace when the program cache is already warm?

  1. The program cache reuses the prepared operation program.
  2. Trace also reuses the captured dispatch sequence, so the host does not repeat the normal per-operation submission path for every inference.
  3. They complement each other: one removes repeated program preparation, and the other reduces repeated host dispatch work.

QJD9-2: How is sharding across chips different from sharding across cores within one chip?

My answer

  1. Mesh sharding decides which tensor portion belongs to each chip. For example, I can split the batch or output-feature dimension across devices.
  2. Within each chip, I still choose the local memory layout: interleaved DRAM (Dynamic Random-Access Memory), or a supported sharded layout across cores and memory resources.
  3. These are two separate decisions. A tensor can be sharded across chips and still use interleaved DRAM within every chip.
  4. For mesh distribution, TT-NN provides tools such as ShardTensorToMesh and ReplicateTensorToMesh. The local memory configuration controls placement within the device.
  5. SPMD (Single Program, Multiple Data) means participating devices can execute the same operation sequence on their local data. It does not mean they share one automatically coherent memory.

Study references, not spoken: mesh distribution and local execution and transformer weights using both a mesh mapper and a local memory configuration. The mesh mapper partitions or replicates tensors; transferring host-resident shards to device memory is a separate step unless the conversion call also specifies the device.

QJD9-3: When would you choose data parallelism instead of tensor parallelism?

My answer

  1. If the model fits on one chip and the goal is more total requests per second, I would first consider data parallel inference: replicate the weights and give different requests or batch slices to different chips.
  2. Each chip can then process its own inputs without a collective after every layer. Independent replicas can also be scheduled separately.
  3. If the model does not fit on one chip, or one request needs more compute than one chip can provide efficiently, I would evaluate tensor parallelism: split tensors and operation work across chips.
  4. Tensor parallelism adds communication. I would choose it based on memory capacity, latency, and measured communication cost, not only the number of chips.
  5. Pipeline parallelism is another option: assign different layer groups to different chips, but account for activation transfers, stage imbalance, and pipeline bubbles.

Study reference, not spoken: data-parallel inference test: batch sharding, weight replication, and output reconstruction. These answers concern inference; data-parallel training also requires gradient synchronization.

QJD9-4: How would your K-split and N-split matrix multiplication ideas extend to two chips?

My answer

  1. I would start from C = A × B, where A is the input activation matrix, B is the weight matrix, and their sizes are M by K and K by N.
  2. With N-split, I split B by output-feature columns and make the required A activations available on both chips, by replication or supported communication. Chip zero calculates C0 = A × B0, and chip one calculates C1 = A × B1. These results contain different output columns.
  3. I can keep those columns distributed if the next operation supports that layout. If every chip needs the complete output, I would use all-gather to assemble the columns on each chip.
  4. With K-split, I split A's input-feature columns and the matching rows of B. Each chip calculates a partial result for the same output: P0 = A0 × B0 and P1 = A1 × B1.
  5. The final result is C = P0 + P1. I would use sum all-reduce if every chip needs the complete result, or sum reduce-scatter if the next operation needs only a supported partition of that result.
  6. I would choose the split together with the next layer's input layout. To avoid counting bias twice, I would add it once after the sum, then apply any nonlinear activation. I would retain distributed intermediate data when the next layer can consume it directly.

Study references, not spoken: current transformer MLP (Multi-Layer Perceptron) sharding and collective calls and TT-NN all-reduce implementation, including sum and mesh-axis handling.

The two-chip equations are a proposed explanation of tensor parallelism, not a claim that your Bos matrix partitions ran across chips. If only the host needs the final N-split output for validation, host-side reconstruction is different from an on-device all-gather. For reduce-scatter, choose the output partition dimension and device group together, and verify tile alignment and divisibility requirements. The algebra permits uneven partitions, but a particular collective or kernel may require padding or equal-sized shards.

QJD9-5: How do the chips exchange data? Is it through the remote server or the NoC?

My answer

  1. Within a chip, data moves over the NoC (Network-on-Chip). Between connected Tenstorrent chips, device communication uses their supported Ethernet links.
  2. TT-Fabric provides routing across those chip links. A transfer can move from a worker's local memory, through the chip's communication path, to memory on another chip.
  3. TT-NN exposes collectives through its CCL (Collective Communication Library). All-gather concatenates shards in the selected dimension on each participant; it does not add them. Sum all-reduce adds corresponding partial values and returns the result to every participant. Sum reduce-scatter performs that addition but gives each participant only its assigned result partition.
  4. The remote server launches and controls the workload. My remote login connection is not the device-to-device collective data path.
  5. The destination buffer must be ready, large enough, and kept alive until the transfer and its consumers finish. Asynchronous communication still needs correct completion and buffer-reuse ordering.

Study references, not spoken: TT-Fabric chip-to-chip routing and addressing, collectives in the mesh programming guide, and CCL destination-buffer ownership and synchronization. This describes the supported direct device fabric, not an arbitrary network of unrelated remote servers.

QJD9-6: What changes if the chips are attached to different host servers?

My answer

  1. I would separate host coordination from device communication. Multi-host execution needs both a supported device fabric and a consistent process-to-device mapping.
  2. TT-Distributed provides multi-host execution support, and tt-run launches coordinated processes using MPI (Message Passing Interface).
  3. For a single logical mesh spanning hosts, each rank manages its local devices while participating in the same global workload definition. The ranks need consistent allocation and operation ordering.
  4. I would configure the topology and rank ownership, including the Mesh Graph Descriptor where required, rather than assume that two servers reachable by remote login form a mesh.
  5. In this design, host coordination uses the distributed process layer, while device tensor traffic uses TT-Fabric. For separate pipeline-stage meshes, the stack also provides device send/receive communication through mesh sockets.

Study references, not spoken: distributed launch and mesh/rank configuration, multi-host architecture: coordination versus data movement, and multi-mesh sockets and send/receive. The architecture report includes proposal material; the launch and multi-mesh guides describe the available workflow. A TT-Distributed mesh socket is not simply a host TCP (Transmission Control Protocol) socket carrying the model tensors.

QJD9-7: Why might two or four chips give little speedup, and how would you investigate?

My answer

  1. I would compare the same workload and numerical settings, and measure completed execution rather than only host enqueue time.
  2. I would separate local compute time, communication time, and waiting time. Partitioning can reduce useful compute per chip, but replicated work, tile padding, transfers, and synchronization can offset that saving.
  3. Small workloads may not have enough compute to hide communication latency. Larger workloads can be limited by link bandwidth, topology, duplicated data transfers, or an uneven partition.
  4. I would inspect the slowest device and the communication between consecutive layers. A partition that speeds up one matrix multiplication may make the next layer slower.
  5. I would try fewer partitions, a better distribution across the actual links, or keeping intermediate tensors distributed. I would overlap communication only where data dependencies and buffer lifetimes allow it.
  6. For tensor-parallel latency, I would compare single-chip time with multi-chip time where both fit. For data-parallel serving, I would compare total throughput under the same latency target instead.

Study references, not spoken: CCL tuning, device skew, and synchronization costs and current transformer implementation's topology- and mode-specific communication. This is a proposed profiling approach, not a promised linear speedup. If a model cannot fit on one chip, use a smaller comparable baseline or report capacity and throughput without inventing a single-chip timing.

QJD9-8: How would you debug a multi-chip collective that hangs or returns incorrect results?

My answer

  1. I would first confirm device visibility, link health, and that the configured topology matches the physical system.
  2. Then I would run a small standalone collective with known values on two devices before bringing back the model.
  3. I would check that participants agree on the collective order, supported tensor shapes, layouts and types, and the communicating device group. For gather or scatter, I would also check the tensor dimension. A mesh axis selects device groups; it is not a tensor dimension.
  4. I would inspect the last completed stage on each device, because one missing participant or one earlier kernel failure can make the other devices appear to hang inside communication.
  5. I would check input completion, destination allocation, synchronization objects, and whether any buffer was reused too early.
  6. For wrong values, I would compare each local shard before communication and the reconstructed result afterward. For reductions, I would also account for floating-point tolerance and the changed addition order.

Study references, not spoken: all-reduce participant-axis handling, all-gather tensor dimension versus mesh axis, multi-mesh troubleshooting and physical-link testing, and collective buffer and synchronization requirements.

API note, not spoken: the reviewed public all_reduce takes cluster_axis but no tensor dim; it sums corresponding elements across the participating devices. On a non-line mesh, omitting cluster_axis can reduce across all mesh axes. In a hybrid data-parallel/tensor-parallel configuration, select the intended tensor-parallel group so independent requests are not accidentally summed together.

My answer

  1. A correct kernel can fail if the host selects the wrong core, passes incorrect arguments, or loads the wrong executable.
  2. I would first confirm the test configuration, buffer addresses and sizes, program setup, and actual binary being launched.
  3. Then I would inspect the device entry and kernel behavior using the supported diagnostics.

Q10-3: If there is no DPRINT output, does that mean the kernel was never launched?

My answer

  2. I would confirm that a known-working test prints in the same configuration and that the intended instrumented binary was rebuilt and loaded.
  3. Then I would check host progress, executable loading, and available firmware checkpoints before moving the first print earlier.

  3. I would reduce the hardware failure to a small reproduction and compare the last completed steps in each environment.
